## 핵심 차이점

### 1. `request.cookies.get()` 방식

- Route Handler가 **Request 객체에 의존**하여 실행됩니다
- Next.js가 이를 **정적으로 분석 가능한 코드**로 인식할 수 있습니다
- 캐싱이 더 적극적으로 적용될 수 있습니다

### 2. `cookies()` 서버 액션 방식

- **Dynamic API**를 사용하므로 Next.js가 이 Route Handler를 **완전히 동적**으로 처리합니다
- `cookies()` 함수는 런타임에서만 해석 가능하므로 정적 분석이 불가능합니다
- 캐싱을 우회하고 항상 최신 데이터를 반환합니다

## 왜 mutate가 다르게 동작하는가?

javascript

```javascript
// 문제가 있던 방식 - 캐싱이 개입할 수 있음
const authToken = request.cookies.get('auth_token')?.value;

// 잘 동작하는 방식 - 항상 동적으로 실행됨  
const authToken = await getAccessToken();
```

`cookies()` 서버 액션을 사용하면:

- Route Handler가 **매번 새로 실행**됩니다
- SWR의 mutate가 호출될 때마다 **실제로 서버에서 새로운 데이터**를 가져옵니다
- 캐시된 응답을 반환하지 않습니다

## `force-dynamic`의 한계

`export const dynamic = "force-dynamic"`을 설정해도, **Next.js의 내부 캐싱 메커니즘**은 여전히 작동할 수 있습니다:

javascript

```javascript
// force-dynamic이 있어도...
export const dynamic = "force-dynamic";

export async function GET(request: NextRequest) {
  // 이 방식은 여전히 캐싱될 수 있음
  const authToken = request.cookies.get('auth_token')?.value;
  // ...
}
```

## 왜 `cookies()` 서버 액션이 더 확실한가?

javascript

```javascript
// 이 방식이 더 확실한 이유
const authToken = await getAccessToken(); // cookies() 사용
```

1. **Runtime Dynamic API**: `cookies()`는 런타임에서만 해석되는 API입니다
2. **Static Analysis 불가**: Next.js가 빌드 타임에 이 코드를 분석할 수 없습니다
3. **강제 Dynamic 렌더링**: 이런 API가 있으면 Next.js가 해당 Route Handler를 **무조건 동적으로** 처리합니다
